# 完整权限系统实现说明

## 实现概述

根据《虚拟组织和岗位赋权功能说明.md》文档的要求，已完成基于岗位的**功能权限**和**数据权限**的完整实现。用户现在可以通过岗位获得操作权限和数据访问权限。

## 核心功能

### 1. 功能权限系统（操作权限）

用户可以通过岗位获得各种操作权限，如：增加、删除、修改、查阅、上传、下载、导入EXCEL、导出EXCEL等。

#### 实现的函数

##### `get_user_function_permissions(user_id)`
获取用户的综合功能权限（用户自身权限 + 所有岗位的功能权限合并）

**返回值**：
- `'all'` - 拥有所有功能权限
- `['增加', '删除', '修改', ...]` - 权限列表

**权限来源**：
1. 用户自身的 `permissions` 字段
2. 用户所有岗位的 `function_permissions` 字段

**合并规则**：取并集（用户拥有的所有权限）

##### `has_permission(user_id, permission)`
检查用户是否拥有指定的功能权限

**参数**：
- `user_id` - 用户ID
- `permission` - 权限名称（如 '增加', '删除', '修改', '查阅'）

**返回**：`True` / `False`

**示例**：
```python
if has_permission(user_id, '增加'):
    # 用户可以执行增加操作
```

##### `get_user_permissions_string(user_id)`
获取用户权限的字符串表示（用于传递给模板）

**返回值**：
- `'all'` - 所有权限
- `'增加,删除,修改,查阅'` - 逗号分隔的权限列表

### 2. 数据权限系统（数据范围）

用户只能查看和操作其权限范围内的合同数据。

#### 实现的函数

##### `get_user_data_scope(user_id)`
计算用户的综合数据权限范围，返回最宽松的权限级别：
- **'all'** - 全部合同（超级管理员或任一岗位有 all 权限）
- **'org'** - 本组织合同（任一岗位有 org 权限）
- **'custom'** - 自定义合同（任一岗位有 custom 权限）
- **'self'** - 仅自己创建的合同（默认权限）

**优先级**：all > org > custom > self

##### `get_user_accessible_contract_ids(user_id, customer_id)`
获取用户可访问的合同ID列表：
- 返回 `None` 表示可访问所有合同（超级管理员或 'all' 权限）
- 返回 `[]` 表示没有可访问的合同
- 返回具体的合同ID列表

**权限逻辑**：
- **all 权限**：返回 None（不过滤）
- **org 权限**：返回用户所属组织的所有合同ID
- **custom 权限**：返回岗位被授权的合同ID + 用户自己创建的合同ID
- **self 权限**：返回用户自己创建的合同ID

## 应用范围

### 已更新的装饰器

#### `@permission_required(permission)` - 功能权限检查装饰器
**改进前**：只检查用户自身的 `permissions` 字段
```python
if user.permissions and permission in user.permissions:
    return f(*args, **kwargs)
```

**改进后**：整合用户自身权限 + 所有岗位的功能权限
```python
if has_permission(user_id, permission):
    return f(*args, **kwargs)
```

## 完整的权限检查流程

每个请求按以下顺序检查：

### 1. 登录验证
```python
@login_required
```

### 2. 功能权限检查（已整合岗位权限）✨
```python
@permission_required('操作')
```
- 检查用户自身的 `permissions` 字段
- **检查用户所有岗位的 `function_permissions` 字段（新增）**
- 取并集后判断是否有权限

### 3. 租户隔离检查
```python
customer_id = get_current_customer_id()
if customer_id is not None and contract.customer_id != customer_id:
    flash('权限不足', 'warning')
    return redirect(url_for('index'))
```

### 4. 数据权限检查（已整合岗位权限）✨
```python
user_id = session.get('user_id')
if user_id and customer_id is not None:
    accessible_ids = get_user_accessible_contract_ids(user_id, customer_id)
    if accessible_ids is not None and id not in accessible_ids:
        flash('您没有权限操作该合同', 'warning')
        return redirect(url_for('index'))
```

### 完整示例代码

```python
@app.route('/contract/<int:id>/edit', methods=['GET', 'POST'])
@login_required                           # 1. 登录验证
@permission_required('修改')              # 2. 功能权限检查（整合岗位权限）
def edit_contract(id):
    contract = Contract.query.get_or_404(id)

    # 3. 租户隔离检查
    customer_id = get_current_customer_id()
    if customer_id is not None and contract.customer_id != customer_id:
        flash('权限不足：无法访问其他租户的合同', 'warning')
        return redirect(url_for('index'))

    # 4. 数据权限检查（整合岗位权限）
    user_id = session.get('user_id')
    if user_id and customer_id is not None:
        accessible_ids = get_user_accessible_contract_ids(user_id, customer_id)
        if accessible_ids is not None and id not in accessible_ids:
            flash('您没有权限编辑该合同', 'warning')
            return redirect(url_for('index'))

    # 业务逻辑...
```

## 权限整合示例

### 示例1：功能权限合并（取并集）

**用户"张三"的权限配置**：
- 用户自身权限：`查阅`
- 岗位A（项目经理）：`增加,修改,查阅`
- 岗位B（审批人）：`删除,审批`

**综合功能权限**（取并集）：
```
查阅, 增加, 修改, 删除, 审批
```

**结果**：张三拥有所有这些岗位赋予的功能权限。

### 示例2：数据权限取最宽松

**用户"李四"的岗位配置**：
- 岗位A（项目成员）：数据权限=本组织合同
- 岗位B（合同审批人）：数据权限=全部合同

**综合数据权限**（取最宽松）：
```
全部合同
```

**结果**：李四可以访问租户内的所有合同（因为岗位B的权限最宽松）。

### 示例3：复杂场景

**用户"王五"的配置**：
- 用户自身权限：无
- 岗位A（销售）：功能权限=`增加,查阅`，数据权限=`仅自己创建的合同`
- 岗位B（项目经理）：功能权限=`修改,删除`，数据权限=`本组织合同`

**综合功能权限**：
```
增加, 查阅, 修改, 删除
```

**综合数据权限**：
```
本组织合同（org > self）
```

**结果**：
- 王五可以执行增加、查阅、修改、删除操作
- 王五只能访问所属组织的合同（不仅限于自己创建的）

## 特殊情况处理

### 1. 没有可访问合同的情况
当用户没有任何可访问的合同时：
- 合同列表显示为空
- 统计数据为 0
- 导出时提示"没有可导出的合同数据"

### 2. 超级管理员
- 系统超级管理员（admin、superadmin）自动拥有所有权限
- 不受功能权限和数据权限限制
- `get_user_function_permissions()` 返回 `'all'`
- `get_user_accessible_contract_ids()` 返回 `None`（不过滤）

### 3. 没有分配岗位的用户
- 功能权限：使用用户自身的 `permissions` 字段
- 数据权限：默认只能访问自己创建的合同（'self' 权限）

### 4. 组织权限但未分配组织
- 如果用户岗位有 'org' 权限但未分配到任何组织
- 降级为 'self' 权限（只能看自己创建的合同）

### 5. 自定义权限
- 用户可以访问岗位被明确授权的合同
- 同时也能访问自己创建的合同（两者取并集）

## 数据库依赖

本功能依赖以下数据表：
- `position` - 岗位表（包含 `function_permissions` 和 `data_scope` 字段）
- `user_position` - 用户岗位关联表
- `position_contract_permission` - 岗位合同权限表（用于 custom 权限）
- `user_organization` - 用户组织关联表（用于 org 权限）
- `organization` - 组织表

确保数据库已执行 `upgrade_db_virtual_org_position.py` 升级脚本。

## 性能考虑

### 当前实现
- 每次请求都会查询用户的岗位和权限
- 对于大量合同的查询，使用 `IN` 子句过滤
- 权限计算涉及多表关联查询

### 优化建议（未来）
1. **权限缓存**：将用户的综合权限缓存到 session 或 Redis
2. **增量更新**：岗位或权限变更时清除缓存
3. **数据库索引**：为 `contract.created_by` 和 `contract.organization_id` 添加索引
4. **延迟加载**：只在需要时才计算权限

### 测试场景

**场景1：用户自身权限**
- 用户权限=`查阅`

- 预期：只能查看，不能增删改

**场景2：岗位功能权限**

**场景3：权限合并**
- 用户权限=`查阅`
- 岗位A权限=`增加,修改`
- 岗位B权限=`删除`
- 预期：拥有 查阅+增加+修改+删除 所有权限

#### 2. 数据权限测试

**场景1：全部合同权限（all）**
- 创建岗位，数据权限=全部合同
- 分配给用户
- 预期：用户能看到租户内所有合同

**场景2：本组织合同权限（org）**
- 创建岗位，数据权限=本组织合同
- 创建组织A和组织B
- 将用户分配到组织A
- 为组织A和组织B分别创建合同
- 预期：用户只能看到组织A的合同

**场景3：自定义权限（custom）**
- 创建岗位，数据权限=自定义
- 创建5个合同
- 为岗位授权其中2个合同
- 用户自己创建1个合同
- 预期：用户能看到3个合同（被授权的2个 + 自己创建的1个）

**场景4：仅自己创建的合同（self）**
- 用户没有分配任何岗位
- 用户创建2个合同，其他用户创建3个合同
- 预期：用户只能看到自己创建的2个合同

**场景5：多岗位权限合并**
- 岗位A：数据权限=本组织
- 岗位B：数据权限=全部合同
- 预期：取最宽松的权限（全部合同）

#### 3. 综合测试

**场景：复杂权限组合**
- 用户分配到岗位A和岗位B
- 岗位A：功能权限=`增加,查阅`，数据权限=本组织
- 岗位B：功能权限=`修改,删除`，数据权限=自定义（授权合同001、002）
- 用户所属组织有合同003、004、005
- 用户自己创建了合同006

**预期结果**：
- 功能权限：增加、查阅、修改、删除（合并）
- 数据权限：本组织（org > custom），可访问合同003、004、005、006
  - 注意：虽然岗位B只授权了001、002，但因为岗位A有org权限，最终取org

#### 4. 批量操作测试

**场景：批量删除**
- 创建10个合同（001-010）
- 用户只有权限访问其中5个（001-005）
- 用户选择删除001-010全部合同
- 预期：只有001-005会被删除，006-010被跳过
